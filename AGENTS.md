## Fuentes de verdad

Lee antes de planificar o implementar:

1. `docs/decision-register.md`
2. `docs/recovery-implementation-plan.md`
3. `docs/current-state-audit.md`
4. `docs/production-gap-analysis.md`
5. ADR relevantes bajo `docs/adr/`
6. Documentos de producto, arquitectura, seguridad, API, datos, tests y despliegue aplicables

Las decisiones ACCEPTED prevalecen. No se reabre una decisión sin ADR nuevo y actualización explícita del registro.

## Flujo Git obligatorio

- `main` solo puede inicializarse una vez mediante el prompt de bootstrap.
- Después del bootstrap, nunca trabajes, hagas commits, pushes, merges, rebases ni cherry-picks sobre `main`.
- Cada cambio usa una rama nueva.
- Tipos de rama permitidos:
  - `feature/`
  - `bugfix/`
  - `fix/`
  - `update/`
  - `refactor/`
  - `security/`
  - `test/`
  - `docs/`
  - `chore/`
  - `release/`
- Cada rama debe producir una pull request.
- Todas las PR tienen `main` como base.
- Nunca fusiones una PR ni ejecutes `gh pr merge`.
- Nunca cierres una PR salvo orden explícita del usuario.
- El usuario revisa y fusiona desde GitHub.
- Nunca hagas force push.
- No borres ramas remotas mientras existan PR dependientes.

## Commits y atribución

Usa Conventional Commits:

`type(scope): imperative description`

Tipos permitidos:

`feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `build`, `ci`, `perf`, `style`, `revert`

Está prohibido incluir en commits, títulos de PR, cuerpos de PR o documentación de cambios:

- `Cursor`
- `cursor`
- atribuciones del tipo “generated by Cursor”
- footers `Co-authored-by` que atribuyan trabajo a Cursor

Los mensajes deben describir el cambio técnico, no la herramienta utilizada.

## Documentación obligatoria

Toda rama que modifique código, configuración, infraestructura, migraciones, assets o tests debe:

1. Crear o actualizar un registro bajo `docs/changes/`.
2. Actualizar toda documentación canónica afectada.
3. Actualizar el estado real en `docs/implementation-status.md` cuando cambie.
4. Actualizar el recovery plan, auditoría o gap analysis cuando cambie el estado de una fase o gap.
5. Crear o actualizar ADR cuando cambie arquitectura, scope, seguridad, proveedor, persistencia, despliegue o decisión aceptada.

No se acepta una PR de código sin documentación.

## Implementación

- Respeta TypeScript strict.
- No uses `any` sin justificación documentada.
- Mantén separación entre UI, aplicación, dominio e infraestructura.
- No añadas abstracciones especulativas.
- No amplíes el MVP.
- No uses mock ni memory runtime en preview o producción.
- No inventes credenciales.
- No ocultes fallos de proveedores.
- No marques trabajo como verificado sin ejecutar la comprobación correspondiente.

## Verificación

Antes de abrir una PR:

- ejecuta lint;
- ejecuta typecheck;
- ejecuta tests relevantes;
- ejecuta build;
- revisa migraciones;
- revisa seguridad y privacidad;
- revisa documentación;
- usa al verificador independiente.

Si una comprobación no puede ejecutarse, deja la PR como draft y documenta el bloqueo concreto.
